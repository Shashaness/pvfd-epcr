## Threat model

The portable format protects payload confidentiality against a reader of backup objects without the district private key and passphrase. It rejects altered ciphertext, tags, wrapped keys, nonces and authenticated metadata before releasing plaintext. The public key alone can encrypt but cannot decrypt.

Excluded threats include compromised tablets/workstations/OS or app processes, memory inspection, privileged debugging, ransomware/deletion, full valid-object replay/rollback, coerced custodians, stolen unlocked recovery keys, insecure PHI handling after recovery, and malicious replacement of the app's trusted key configuration. Any holder of the public key can create a new valid envelope: encryption is **not sender authentication** or proof of clinical authorship. AEAD does not establish record freshness, prevent backups being omitted, or bind a filename to content. Those need separately reviewed application/operational controls.

Visible metadata consists of cryptographic parameters, public-key fingerprint, ciphertext size, wrapped key and nonce. No patient/report/revision fields appear there. Future object names must be opaque and must not contain patient information. No record naming is generated by the encryption service. Garbage-collected JVM/Python/Dart memory cannot guarantee zeroization; Android wipes its original DEK array best-effort, but provider/library copies can remain. Temporary recovered plaintext can survive abrupt process termination on the authorized workstation; all recovery directories must stay protected.

## Algorithms and implementation

- RSA modulus: exactly 3072 bits; public exponent: exactly 65537.
- Key wrap: RSA-OAEP, message digest **SHA-256**, MGF1 digest **SHA-256**, empty label. Android passes an explicit `OAEPParameterSpec`; no provider padding defaults are trusted.
- Payload: AES-256-GCM, fresh CSPRNG-generated 32-byte DEK per operation, fresh 12-byte nonce, full 16-byte tag.
- Android randomness: platform `SecureRandom`, also supplied to OAEP. There are no injectable production random sources, fixed keys or caller-supplied IVs.
- Each DEK is used for exactly one encryption, then discarded. Thus there is no repeated encryption under a persistent DEK and no dependency on Milestone 4.1's nonce ledger. Random-value collision risk is negligible, not mathematically zero. Tests verify distinct DEKs and nonces for their samples; they cannot prove RNG quality for every future device/operation.
- Android established JCA/JCE implementations handle RSA/AES. The JCA RSA transformation name `RSA/ECB/OAEPPadding` is the platform RSA alias, not AES-ECB or block-mode encryption of the payload.
- Python `cryptography` 49.0.0 handles RSA key generation/unwrapping, PKCS#8 encryption and AES-GCM authentication. It is pinned in `tools/requirements-recovery.txt`, for the workstation only. No new Dart/Flutter or Android runtime package was added.

`lib/services/recovery/recovery_encryption_service.dart` exposes byte-oriented `RecoveryEncryptionService`, `PublicRecoveryKey`, an Android adapter and a structural envelope parser. `loadPublicKey` accepts canonical DER SubjectPublicKeyInfo and an expected ID; native validation must succeed before creating a public-key handle. `encryptForRecovery` snapshots bytes, calls native encryption and validates the returned envelope structure, key ID and payload length. It never returns a DEK and has no decrypt/private-key API. Native independently validates inputs and caps payloads.

`RecoveryEncryption.kt` has no Keystore, filesystem, JSON, networking or logging dependency. `MainActivity` registers only `validatePublicKey` and `encryptForRecovery` on `com.pvfd3.pvfd_epcr/recovery`, using a background task queue. Registration does not load keys, create files or call the service. No production app code invokes it yet. Android API 24+ is supported subject to actual provider capability; other platforms fail explicitly, with no replacement key or software fallback.

## Portable envelope v1

All integer fields are unsigned big-endian. No optional fields, compression, implicit downgrade, medical JSON interpretation or extension/trailing bytes are allowed. Maximum plaintext/ciphertext is 16,777,216 bytes (16 MiB); maximum whole envelope is 16,777,712 bytes. RSA-wrapped key is exactly 384 bytes; the key ID is exactly 64 lower-case ASCII hex characters, SHA-256 of the **canonical DER SubjectPublicKeyInfo**. It includes the entire public-key structure, not merely the modulus.

| Offset | Size | Meaning |
| --- | --- | --- |
| 0 | 8 | ASCII `PVFDBAK1` |
| 8 | 1 | Envelope version `1` |
| 9 | 1 | Algorithm `1`: RSA-3072 OAEP-SHA256/MGF1-SHA256 + AES-256-GCM |
| 10 | 2 | Key-ID length, must be `64` |
| 12 | 2 | Wrapped-DEK length, must be `384` |
| 14 | 1 | Nonce length, must be `12` |
| 15 | 1 | Tag length, must be `16` |
| 16 | 4 | Ciphertext length N, 0–16,777,216 |
| 20 | 64 | Lower-case hex SPKI SHA-256 fingerprint |
| 84 | 384 | OAEP-wrapped 32-byte AES key |
| 468 | 12 | GCM nonce |
| 480 | N | Ciphertext |
| 480+N | 16 | GCM authentication tag |

AAD is the exact ASCII string `PVFD/ePCR/recovery-backup/v1`, a zero byte, then **all 480 header bytes**. This authenticates all version/algorithm/length fields, key ID, wrapped key and nonce. No additional external AAD is required. Python decrypts with an empty OAEP label and `ciphertext || tag`, using exactly those AAD bytes. Modified metadata that is still structurally valid fails authentication; malformed/unsupported fields are rejected before cryptographic dispatch. A modified wrapped key usually fails OAEP first. There is no compatibility fallback to Milestone 4.1.

## Operational key generation and custody

No operational district key was generated in this milestone. Tests generate explicitly synthetic keys under secured OS temporary directories and clean them up. Only a development **public** key is committed in a Dart test fixture; its matching private key was discarded without serialization. It is never a production default and cannot provide district recovery.

On an authorized offline POSIX workstation, install the reviewed Python dependency in a dedicated environment, using a trusted package source or verified offline wheel set:

```sh
python3 -m venv /secure/recovery-python
/secure/recovery-python/bin/python -m pip install -r tools/requirements-recovery.txt
/secure/recovery-python/bin/python tools/pvfd_generate_recovery_keys.py \
  --private-output /secure/private-custody/pvfd-recovery-private.pem \
  --public-output /secure/public-provisioning/pvfd-recovery-public.pem
```

The tool prompts with `getpass`, confirms the phrase and refuses an echoed-input fallback. No passphrase flag, environment-variable interface or passphrase printing exists. Use a unique high-entropy randomly generated passphrase; the enforced 16-character minimum is only a guardrail, not an entropy guarantee. Maximum UTF-8 length is 1024 bytes. The library's `BestAvailableEncryption` serializes the private key as encrypted PKCS#8 PEM; cleartext private keys are never written. Public output is SubjectPublicKeyInfo PEM. Only the nonsecret public fingerprint is printed.

Private/public output paths must have separate parent directories. Files are created as mode 0600 in owned mode-0700 directories. Symlink/path-traversal output paths and overwrites are refused. Existing directory permissions are not silently relaxed or changed. Private output under a Git checkout is refused, including an ignored key path. The tool is never called from app startup/import. Tests do not generate operational district keys. Generation of the two files is not pair-wide transactional: if public publication fails after private creation, the encrypted private file may remain. Stop and review custody; do not delete or overwrite it automatically.

The district must designate authorized custodians, record the trusted fingerprint through an independently verified channel, and maintain multiple separately secured offline copies of the encrypted private key. Keep the passphrase in independently controlled recovery custody, not beside the key. Test restoration on an authorized workstation before operational activation and periodically thereafter; document loss/revocation/rotation procedures. Losing the private key or passphrase makes corresponding backups unrecoverable. Compromise allows recovery of retained backups for that key; there is no forward secrecy.

**Never put the private recovery key or its passphrase on a tablet, in Android Keystore/assets, in the source repository/GitHub, in S3, or in any backup object.** Protect even passphrase-encrypted private files as district secrets. Temporary encrypted test keys do not establish an operational custody process.

## Public-key installation and rotation

The public key's authenticity is essential: a substituted public key sends future backups to an attacker's recovery key. The caller must obtain the expected fingerprint from trusted district configuration, not derive a new expected value from an untrusted downloaded key and assume that is verification. A compromised signed app/configuration is outside this mechanism's protection.

For future provisioning, verify custody and the expected fingerprint independently. Convert the generated public PEM to canonical DER on the trusted workstation, for example:

```sh
openssl pkey -pubin -in /secure/public-provisioning/pvfd-recovery-public.pem \
  -outform DER -out /secure/public-provisioning/pvfd-recovery-public.der
```

Then, in a separately reviewed activation change, install **only** those public bytes and the independently pinned ID into a signed app/trusted configuration. Call `loadPublicKey(derBytes, expectedId)` explicitly. This phase deliberately adds no asset declaration, active configuration, startup call, public-key download or operational default. Native code rejects noncanonical/trailing DER, non-RSA keys, wrong modulus/exponent and fingerprint mismatches. Missing/malformed configuration fails; it never generates or substitutes a key. The Python public loader validates canonical DER or a single canonical SPKI PEM block.

Each key has its own fingerprint. Rotation explicitly selects a new trusted public key/ID for future backups; retain matching older encrypted private keys and passphrases for retained older backups. Recover one key's objects per CLI invocation; mismatched IDs fail individually, never fall back to another key. Changing algorithms, lengths or OAEP label requires a newly specified version/algorithm, not an in-place reinterpretation of version 1.

## Offline Python recovery

Recovered plaintext may be sensitive PHI. Use an authorized secured POSIX workstation with protected storage, access controls, appropriate retention and no unapproved synchronization. POSIX directory-FD/no-follow operations and atomic hard-link publication are required; Windows and filesystems without these primitives are unsupported and must fail rather than degrade path/overwrite safeguards. Paths containing symlinks (including symlink ancestors) are rejected; supply physical paths where OS aliases such as `/tmp` are symlinks.

```sh
python3 tools/pvfd_recover.py \
  --private-key /secure/private-custody/pvfd-recovery-private.pem \
  --input ./encrypted-backups \
  --output ./recovered-epcrs

python3 tools/pvfd_recover.py \
  --private-key /secure/private-custody/pvfd-recovery-private.pem \
  --input ./encrypted-backups --recursive --verify-only
```

`--input` accepts one file or a directory. Directory mode selects regular `*.pvfdbak` files; recursion is opt-in. It preserves safe relative subdirectories and appends `.recovered` to input filenames because payloads are arbitrary bytes, not necessarily JSON. It does not interpret patient data or trust envelope-supplied filenames. The output tree must be disjoint from the input path, including parent/child overlap. Do not use PHI-bearing input filenames. Missing/no selected files count as failures.

The tool prompts securely for the encrypted private-key passphrase, checks its RSA parameters and each envelope fingerprint, validates exact lengths/version/algorithm, unwraps the DEK and authenticates the full payload in memory. Input/key reads are bounded and reject symlinks and special files, including FIFOs. Authentication failure produces no plaintext file or plaintext temporary file. `--verify-only` performs the same unwrapping/authentication but creates no output directory/files and ignores `--output`.

After successful authentication, output is written to an exclusive random mode-0600 sibling temporary file, flushed/fsynced, then atomically linked to a new final filename with no-overwrite semantics. Symlink/no-follow checks and directory-relative operations protect traversal; directories are owned mode 0700. No overwrite flag exists. The temporary file is removed on handled failure. Abrupt termination can leave a plaintext temporary file in that protected directory; after publication a filesystem/fsync failure can leave a complete output despite a failure status. Operator review is required; never assume retries may overwrite. Multi-file processing is not an all-or-nothing transaction: successful files remain if others fail.

Only safe fixed error codes and aggregate success/failure counts are printed, not filenames, paths, private keys, plaintext or full backup objects. Exit codes: `0` all selected files succeeded; `1` one or more file/traversal failures (possibly partial success); `2` setup/key/passphrase/argument or other operation failure. Wrong passphrase cannot reveal plaintext. Private-key unlock/corruption errors are intentionally not distinguished cryptographically.

## Tests and repeatability

Python tests use temporary synthetic RSA keys, encrypted test PEM files and synthetic byte payloads. No actual patient files are used. Run:

```sh
python3 -m unittest discover -s tools/tests -v
python3 -m compileall -q tools
```

Host Flutter tests validate service/channel contracts, explicit public provisioning, safe errors and strict envelope parsing alongside all 100 previous tests. Native Android tests execute the production `RecoveryEncryption` implementation. They test the Python-computed fingerprint, public-key rejection, synthetic JSON, empty/Unicode/1 MiB/binary payloads, repeated encryption and operation after deletion of an **isolated synthetic** Keystore key. No existing device keys are enumerated or deleted. This simulates loss of all local keys used by this test; deleting every real tablet Keystore key would be destructive and was not done.

To repeat native interoperability, first run the required Flutter checks/build. In `pvfd_epcr/android`, build the separate test APK with:

```sh
./gradlew :app:assembleDebugAndroidTest \
  -PpvfdTestRunner=com.pvfd3.pvfd_epcr.RecoverySelfTestInstrumentation
```

Identify the authorized device with `flutter devices` and `adb devices -l`. Independently compare installed/candidate package version and public signing certificate; stop on a conflict. Use direct `adb install -r -t` for the app and test APK with no uninstall/clear-data/downgrade fallback. This never starts the ePCR editor. Then, with SDK platform-tools on PATH:

```sh
python3 tools/tests/android_recovery_interop.py --device DEVICE_ID
```

This explicitly invoked harness generates temporary **test-only** recovery keys via the key-generation implementation, keeps its encrypted private PEM/passphrase on the workstation, sends only DER public bytes to a fresh app-cache test directory, and runs the headless test. It fetches only seven known synthetic ciphertext files, independently decrypts all seven with Python, compares exact original bytes, unwraps the test DEKs in memory to verify 32-byte/distinct keys and distinct 12-byte nonces, and runs both verify-only and directory recovery. The final sample is encrypted after deleting the test's only local Keystore key. It removes only its own explicitly named device files/directory and host temporary tree. It never launches Flutter/UI or enumerates/reads clinical records. Device tests plus independent Python decryption establish cross-language cryptographic interoperability; Dart channel tests are host mocks, not a live Dart-engine/device end-to-end run.

## S3 integration requirements and remaining risks

Future S3 must hold **encrypted backup objects only**, never plaintext ePCRs, private recovery keys or passphrases. Nothing contacts S3 in this phase. Before activation, separately design authenticated upload permissions/credentials, TLS, opaque object names, key-ID selection, retry/atomic completion/integrity checks, object versioning/retention/deletion, offline queues, district authorization, auditing, public-key distribution/rotation, and recovery drills. S3 server-side encryption can be additional protection; it does not replace this client-side recovery format.

The public key grants no permission to export PHI. Future production backups require reviewed policy/custody and data handling. Migration/local encryption activation, automatic synchronization, biometrics/access policy and all existing signing/export-cache/backup/operational risks remain outside this milestone.

The source publication inventory is updated only for reviewed source, tests, requirements and documentation. Ignore rules exclude portable backup objects, key files, Python caches and virtual environments. The local publication scanner's exact allowlist adds only the named new tools/tests; its private-key detection also recognizes actual encrypted-private-PEM blocks without suppressing existing unencrypted-key checks. No operational key, patient data, private signing material, release, tag, push or APK distribution is part of this milestone.
